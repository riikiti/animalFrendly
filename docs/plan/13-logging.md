# Логирование

[← к оглавлению плана](../PLAN.md) · инфраструктура сбора логов — [`../deploy/06-logging.md`](../deploy/06-logging.md)

Два разных журнала, которые не подменяют друг друга:

- **Операционные логи** (этот документ) — для отладки и мониторинга, живут в системе
  сбора логов (см. [`../deploy/06-logging.md`](../deploy/06-logging.md)), хранятся
  ограниченное время, могут содержать техническую информацию.
- **`audit_logs`** (см. [`../database/07-notification-media-moderation.md`](../database/07-notification-media-moderation.md))
  — бизнес-события (кто и что подтвердил, кто провёл верификацию, решение по спору),
  постоянное хранение в БД, используется поддержкой/юристами, не заменяется логами.

## Формат

- Все логи backend — **структурированный JSON** (Monolog JSON formatter), не текстовые
  строки. Каждая запись включает: `timestamp`, `level`, `message`, `channel`, а также
  контекстные поля ниже.
- Приложение пишет логи **только в stdout/stderr**, никогда в локальный файл контейнера —
  файловая система пода/контейнера эфемерна и теряется при перезапуске (12-factor app).
  Сбор и хранение — задача инфраструктуры ([`../deploy/06-logging.md`](../deploy/06-logging.md)),
  не приложения.

## Корреляция запросов

- Middleware на входе присваивает каждому HTTP-запросу `request_id` (берётся из заголовка
  `X-Request-Id`, если пришёл от клиента/Ingress, иначе генерируется). Значение кладётся в
  контекст логов (Laravel `Context::add('request_id', ...)`) — попадает в каждую строку
  лога за время обработки запроса без ручной передачи.
- При постановке задачи в очередь (обработка вебхука ЮKassa, отправка уведомления)
  `request_id` исходного запроса передаётся в payload джобы и восстанавливается в контекст
  логов внутри `handle()` — чтобы асинхронную обработку можно было проследить до
  исходного запроса, инициировавшего её.
- Аутентифицированные запросы дополнительно логируют `user_id` (не email/телефон — см.
  ниже).

## Уровни

| Окружение | Минимальный уровень в общий канал | Примечание |
|---|---|---|
| local | `debug` | всё, включая SQL-запросы при необходимости |
| staging | `info` | |
| production | `info` для бизнес-событий, `warning` для фреймворка/инфраструктурного шума | не заглушать `error`/`critical` никогда |

Бизнес-события (оплата принята, сделка переведена в `paid_escrow`, авто-подтверждение
сработало, верификация приюта одобрена) логируются на уровне `info` с именем события в
формате `модуль.событие` (`marketplace.order.paid_escrow`, `shelter.verification.approved`)
— это то, по чему потом строятся алерты и дашборды, см.
[`../deploy/06-logging.md`](../deploy/06-logging.md).

## Что запрещено логировать

- Пароли, токены доступа, ключи ЮKassa/FCM/S3, заголовки авторизации целиком.
- Персональные данные без маскирования: телефон/email — только частично
  (`+7 (9**) ***-**-42`), полные ФИО — не логировать, только `user_id`.
- Сырые данные банковских карт (в любом случае не проходят через backend — их принимает
  напрямую виджет ЮKassa, но правило фиксируется явно, чтобы не появилось логирования
  ответа ЮKassa целиком без фильтрации).
- Полное тело вебхука ЮKassa с подписью — логировать структурированно нужные поля
  (`payment_id`, `status`, `order_id`), не сырой payload с секретными заголовками.
